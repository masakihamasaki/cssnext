# 事務所としての運用

このワークフローを「ライバー支援の取り組み」に載せるときの、人・時間・責任の置き方。

## 何が変わるか

これまで（ライバー1人あたり / 週）:

| 作業 | 時間 |
| --- | --- |
| 切り抜き探し | 60分 |
| 編集・テロップ | 120分 |
| 文言を考える | 30分 |
| 投稿 | 20分 |

これから:

| 作業 | 時間 |
| --- | --- |
| 切り抜き書き出し・登録（週1回まとめて） | 60分 |
| 計画の確認と差し替え | 10分 |
| フック型の改善（`report` を見て） | 20分 |

削れるのは編集と投稿の反復であって、素材づくりと判断は削れない。
**空いた時間をフック改善と本人フィードバックに回す**のが、この仕組みを入れる理由。

## 週次サイクル

| 曜日 | 作業 | 担当 |
| --- | --- | --- |
| 月 | 前週の `report` を見る。切り口テストの勝ち負けとフック型の増減を決める | マネージャー |
| 月 | 配信アーカイブから切り抜きを書き出し、`livers.json` に登録 | 編集担当 |
| 火 | `lsw plan --days 7 --seed <週番号>` → 内容を本人と確認 → `--commit` | マネージャー＋本人 |
| 火 | `lsw build --execute` → `lsw queue` | 編集担当 |
| 毎日 | `lsw publish`（cron）→ 本人が下書きを確認して公開 | 自動＋本人 |
| 日 | 各アカウントのインサイトを CSV に落とす | マネージャー |

計画は必ず本人に見せてから commit する。
「知らないうちに自分の切り抜きが投稿されていた」を起こさないための一手間。

## 役割と責任

| 役割 | 持つもの |
| --- | --- |
| ライバー本人 | 素材の利用同意、アカウント認可、**公開の最終判断** |
| マネージャー | フック型の設計、計画の承認、数字の解釈 |
| 編集担当 | 切り抜きの書き出しと登録、ビルド実行 |
| ワークフロー | 割り当て・生成・予約・投稿の反復作業 |

公開の判断がライバー本人にあることは動かさない。
既定の投稿先を下書き（inbox）にしているのはこのため。

## ガードレール

設定と実装で強制しているもの:

- `consent: true` の素材しか使わない。同意の撤回は `consent` を `false` にするだけで即座に効く
- `authorizedAt` のあるアカウントにしか投稿しない。認可が切れたらこの項目を消す
- 素材は14日、フックは7日のクールダウン。使い回しはしない
- 同日に同じ文面を複数アカウントへ出さない
- 素材が足りなければ投稿枠を空ける（埋めるための使い回しをしない）
- 公開実行には `LSW_ALLOW_PUBLISH=1` が要る。cron に入れるまで意図的に一段挟む

AI生成素材レーンで実装が強制しているもの:

- 生成プロンプトとモデルの記録が無い素材は使わない
- 本人の姿を生成した素材は、肖像の明示同意が無ければ使わない
- キャプションに開示文と `#AI生成` が必ず入る（ハッシュタグ上限で押し出されない）
- AI素材を含む投稿は直接公開しない（本人の下書きに固定）

運用で守るもの（実装では強制できない）:

- **未成年ライバー**の素材は保護者同意の記録を別途残す。この仕組みは同意の有無しか持たない
- 第三者（コラボ相手・リスナーの声・BGM）が写り込む切り抜きは、その権利者の許諾を確認してから登録する
- 各プラットフォームの規約は変わる。特に自動投稿と複数アカウント運用の扱いは定期的に確認する
- 炎上時は該当ライバーの `authorizedAt` を消して `lsw plan` を回せば、その時点で計画から外れる。
  投稿済みのものは各アカウントから手で削除する

## AI生成素材をどこまで使うか

「AI動画だと気づかれるか」は判断基準にしない。気づかれないから使ってよい、にはならない。
判断は次の3点で切る。

| 用途 | 可否 | 理由 |
| --- | --- | --- |
| グッズカット・背景・b-roll・フック用の抽象背景 | 使う | 本人の人格を代弁しない補助映像 |
| 配信の様子の「再現」映像 | 使わない | 実際に無かった配信をあったように見せることになる |
| 本人の顔・声のAI生成 | 原則使わない | やるなら肖像の明示同意と、投稿ごとの本人確認まで含めて設計する |
| 他のライバー・リスナーの姿 | 使わない | 同意を取る相手が特定できない |

開示は「バレたときの保険」ではなく、**ライバー本人が視聴者に嘘をつかないための線**として置く。
事務所が本人の名義で出す投稿である以上、後から責任を負うのは本人になる。

広告としての表示義務（景品表示法のステマ規制、各プラットフォームのAI生成コンテンツ表示など）は
別途かかる。ここが変わりうる領域なので、四半期に一度は現行のルールを確認すること。

## 切り口テストの回し方

1. 素材を1つ選び、型の違うフックを3本当てる（`lsw plan --experiment`）
2. 3日間隔で3本出す。1ラウンドで判定はしない
3. 2週間後、同じ素材でもう1ラウンド。前回と同じ切り口が優先して当たる
4. 各切り口が2本・1000再生に届いたら `report` が勝ちを出す
5. 勝った型を `hookTypes` の中心に据え、負けた型はその素材では使わない

同時に走らせるテストは1ライバーにつき1本。
複数の素材で同時にテストすると、投稿枠がテストで埋まって通常投稿が痩せる。

## KPI

投稿本数は KPI にしない（本数は仕組みで増やせてしまうため）。見るのは：

| 指標 | 意味 | 見方 |
| --- | --- | --- |
| 3秒視聴維持率 | フックの強さ | 型別に比較。50%を下回る型は捨てる |
| 切り口テストの決着数 | 学習が進んでいるか | 月に1件も決着しないなら本数か閾値を見直す |
| プロフィール遷移率 | 配信への導線 | 1%を下回るなら CTA と切り抜き選びを見直す |
| 新規フォロー | 認知の拡大 | 週次の傾向で見る。単発のバズに引っ張られない |
| 配信同接・ギフト | 支援の成果 | 投稿と同接の相関を月次で見る |
| ライバーの作業時間 | 本人の負担 | 増えていたら仕組みが間違っている |

最後の1つを外さないこと。
支援の名目で本人の作業が増えるなら、それは支援になっていない。

## 導入の順序

1. **1人 × 1アカウント × 下書き運用**で2週間。ここで数字の見方を作る
2. 3人に広げる。フック型を本人ごとに分ける
3. `publish` を cron に載せる（下書き送りのまま）
4. 直接公開に切り替えるかは、本人ごとに判断する。全員一律にしない
